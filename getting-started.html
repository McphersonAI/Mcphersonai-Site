Getting Started

Start a technical evaluation.

Choose one runtime path. Check the package and its use rights, inspect locally, then connect an approved installation to Hosted. A Founding Builder application is not required for local technical inspection.

  • Use synthetic data or an explicitly authorized test or staging workflow. Keep existing approval controls in place.
  • Use Node.js 22 or newer for either package. Confirm the documented runtime requirements and your environment fit.

Local Node 0.1.7 · n8n.

Install the public package, then inspect one locally exported n8n workflow. These commands do not pair an installation or start runtime observation.

npm install -g @mcpherson-ai/observa-local-node@0.1.7
observa --version
observa --help
observa status
observa inspect-workflow --file ./workflow.json

Export the test workflow from n8n to workflow.json first. Inspection reports static structure; it does not run the workflow, evaluate policy or verify an outcome. Do not upload the export here.

For runtime observation, you need an approved Hosted invitation and a signed installation composition. Continue with access and pairing below. Inspect the versioned package README and source.

OpenClaw v0.7.4.

First confirm permission to use the package. The release declares OpenClaw plugin API ≥2026.8.2 and Node.js ≥22. Follow the release install procedure:

openclaw plugins install clawhub:@mcphersonai/mcpherson-governance-openclaw
# Restart your OpenClaw gateway, then:
observa --version
observa --help
observa status
observa agents
observa activity
observa decisions

The ClawHub install command is not version-pinned: check that observa --version reports 0.7.4 before following this version’s instructions. On gateway start, the plugin creates a launcher beside the OpenClaw launcher where supported. It does not overwrite another package’s observa command. The launcher does not support Windows; use the released README’s direct-path instructions there.

Local views read the selected OpenClaw profile. They do not probe Hosted, grant authorization or establish business success. Troubleshoot a missing or conflicting command.

Request and confirm Hosted access.

For Hosted commands, set OBSERVA_HOSTED_URL to the HTTPS endpoint supplied for your evaluation. The variable below is a placeholder for that approved endpoint, not a public service address. If you do not have one, ask support for the evaluation endpoint. The CLI still performs email verification and access review; email to support does not grant access.

observa request-access --api-url "$OBSERVA_HOSTED_URL"
observa request-status
  • Follow the CLI’s email-verification prompt and review the metadata before confirming the request.
  • Human review determines access. A request is not an account, paid entitlement or approval to collect production data.
  • After approval, redeem the invitation, review the onboarding agreement, then create a pairing code in Hosted.
  • Pair the correct runtime path using the commands below.

Do not send pairing codes in email or put them in command-line arguments. A download or successful local inspection does not bypass these steps.

Pair the correct package.

Local Node · uses --base-url

observa pair --base-url "$OBSERVA_HOSTED_URL" --code-stdin
observa install
observa diagnose
Paste the single-use pairing code on standard input, then end input (Ctrl-D on Unix-like terminals). Install retrieves and verifies the signed manifest issued for this installation. Diagnose checks local integrity and configuration; it is not proof of end-to-end delivery.

OpenClaw · uses --api-url

observa pair --api-url "$OBSERVA_HOSTED_URL"
observa hosted-health
observa identify
Pair reads the code at a hidden terminal prompt, or accepts an owner-only file with --code-file. Health and identify contact Hosted; they do not produce workflow activity or business-outcome evidence.

Activate the n8n observation path.

After Local Node install and pairing, configure a local loopback credential of at least 24 characters, then generate the n8n hook environment. Replace the illustrative value below with a new local secret. The CLI takes this config value as an argument; protect shell history and process visibility on the host.

observa config set n8n_loopback_credential 'REPLACE_WITH_A_LOCAL_SECRET_24_PLUS_CHARACTERS'
observa n8n-setup
observa start

Load the environment file produced by n8n-setup into your n8n service or container and restart n8n so it loads the hook. Observa does not configure or restart n8n for you. Do not add an Observa workflow node. The observer and n8n must have the loopback connectivity required by the package’s deployment instructions.

The service and loaded hook must be from the same release. After upgrades or rollbacks, regenerate the hook, restart n8n, run one test workflow and check observa diagnose. A diagnose result before an execution does not prove that n8n loaded the new hook.

Run one synthetic workflow. Check the evidence.

  • Run a small authorized test action through the selected runtime. Record what result you expect in the test system.
  • Inspect local activity and, where a mapping and enough context exist, SHADOW decisions. An unmapped action is not a policy verdict.
  • Open the paired workspace in Hosted and confirm the expected action appears for the correct installation. A healthy connection alone does not establish that evidence arrived.
  • For n8n, run observa diagnose after the execution and confirm the service, hook copy and loaded hook match.
  • Compare any available outcome check with the system of record. COMPLETED is not VERIFIED, and VERIFIED does not establish AUTHORIZED.
  • If evidence is absent or uncertain, preserve that state and follow troubleshooting.

Outcome verification is still being qualified with founding workflows. Coverage depends on the runtime, mapping, workflow version and available system-of-record evidence. Missing evidence remains unresolved.

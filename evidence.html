Public Benchmark & Evidence Standard v0.1.

This is the publication standard for evidence on this site. The v0.1.9 result below is a representative engineering reference with explicit limitations, not formal quiet-environment performance qualification. Release identity checks alone are not benchmarks.

Identify the test and its scope

  • Give every result a stable benchmark ID and name the benchmark-standard version.
  • Identify the exact Observa version, source commit/tree where public and appropriate, and artifact hash. State whether the result applies to the current release or a historical one.
  • Identify the runtime and version, CPU, memory, operating system, storage and filesystem, container/VM layout, and network topology. Include where durable storage sits relative to the runtime and observer.
  • Declare warm/cold state, workload size, concurrency or requests per second, sample count and the workload class. Label workloads CONTROLLED SYNTHETIC unless a separately authorized class applies.

Define the measurement before running

  • Publish the precise timer start and stop events, the baseline and paired comparison, and which synchronous and asynchronous work is inside the timer.
  • For latency, report p50, p95, p99 and maximum, including absolute added latency. Relative workflow context may accompany those numbers only with a predeclared representative workflow profile.
  • Where capture applies, report expected and durable captures, loss, duplicates, refusals, corruption and join/integrity failures. Where correctness applies, state expected verdicts and the incorrect verdict count.
  • Predeclare the acceptance gate, run-selection rules and aggregation method. Report accepted and excluded runs with exclusion reasons. Do not select a favorable run after seeing the results.

Classify the whole result

  • Compute PASS, HOLD or FAIL mechanically using the predeclared gate. Each result defines the conditions for all three classifications.
  • Show the target, observations, what passed, what did not, confounders and known limitations. A favorable durability or correctness sub-result cannot override an unmet gate.
  • Gate changes require a new public standard/version and apply only to subsequent results. They never reclassify prior runs retroactively. Keep superseded and unfavorable published results accessible with their original labels.
  • Label evidence SELF-RUN until a third party has reproduced that exact result. Internal review is not independent external audit. Verification fixtures are FIXTURE CONFORMANCE, not qualified external verification or universal runtime support.

Make reproduction possible without exposing private data

  • Link the methodology and, where safe, a reproduction kit: scripts, synthetic fixtures or data, environment specification and run instructions.
  • Use dedicated test environments whose topology can be disclosed. Development or mixed-use measurements may be disclosed as limited reference measurements; they do not become formal quiet-qualified or production performance claims.
  • Where safe, provide sanitized machine-readable artifacts with the same benchmark ID as the human page. Remove secrets, private hostnames/IPs, internal identifiers and customer or partner data.
  • Handle deliberately triggerable evidence-loss or security findings through coordinated disclosure. Repair or contain the issue before publishing exploit-enabling details.
  • Do not make named competitor performance comparisons at launch. Methodology, timer and topology differences must remain visible.

Tested runtime boundary

  • n8n 2.45.7 in regular execution mode.

Current evidence path

Native runtime events → thin adapter → authenticated local acquisition and durable signed evidence → asynchronous Hosted delivery → scoped reporting. A completed runtime action is not proof of a real-world business outcome. Outcome verification requires an authorized downstream system-of-record check.

Environment and timing

The existing b4 Linux ARM64 guest had 4 vCPU and 4 GiB RAM, Ubuntu 24.04.4, Docker 29.5.2 with classic overlay2 and external-SSD storage. Stock n8n 2.45.7 ran on Alpine/musl with Node 26.12.1 in a 3 CPU / 3 GiB container. The Mac host was Apple M4, 10 CPUs and 16 GiB RAM. Workload: one synthetic manual-trigger workflow, concurrency one, 200 alternating OFF/ON pairs per condition; local delivery fixtures were healthy, delayed by 500 ms or unavailable with HTTP 503. No production Hosted endpoint was used.

Total latency runs from the manual-start request to completion-monitor arrival. Synchronous pre-return is the measured native-source projection plus external-hook time; asynchronous Hosted delivery and the remaining lifecycle are outside that timer. OFF disables capture but retains the idle sidecar and source server, so this is not a complete installed-versus-uninstalled footprint comparison.

CPU, memory, storage and delivery

Mean observed n8n CPU per OFF/ON execution was 55.20/56.85 ms (healthy), 52.85/56.20 ms (slow), and 53.35/55.95 ms (unavailable), using coarse 100 Hz process ticks. Whole-sidecar CPU was 1,331.501 / 1,159.223 / 1,212.092 ms; peak sidecar RSS was 139,480 / 138,184 / 142,068 KiB. These include startup and instrumentation, not an isolated causal CPU or memory increment.

Final local journal sizes were 1,249,280 / 1,622,016 / 1,810,432 bytes; pre-stop WAL sizes were 943,512 / 502,672 / 576,832 bytes. These are logical retained-state observations, not write amplification or a long-term storage forecast. Healthy delivery acknowledged 200 receipts; slow delivery had 116 acknowledged and 84 pending; unavailable delivery retained 200 pending. Separate functional tests establish bounded replay, not an all-delivered claim for this short measurement.

Coarse CPU counters, shared memory/GC history, unquantified Mac background interference, instrumentation overhead, a single workload and local synthetic delivery limit causal and production generalization. Blocked background n8n network requests were retained in the raw record; measured workflows succeeded. Clean restart and consistent logical restore are not power-loss or disaster-recovery tests.

Canonical limitations.

This section is the single source for current website limitations. Read it with the release identities above and the scope of any individual evaluation.

Authority

SHADOW ONLY · AUTHORITY NONE · ENFORCEMENT OFF

Observa has no authority to block, approve or rewrite workflow actions. WOULD_DENY is counterfactual, not evidence that anything was blocked. Your existing authorization controls remain necessary.

Evidence and verification

AUTHORIZED != COMPLETED != VERIFIED. Runtime completion is not business-outcome verification; VERIFIED does not prove authorization. Outcome verification is still being qualified with founding workflows. Missing, unmapped or insufficient evidence stays unresolved. Fixture conformance is not external qualification.

Runtime and version scope

The public paths documented here are OpenClaw v0.7.4 and Local Node 0.1.9 for the tested Linux / n8n 2.45.7 regular-mode configurations above. Exact environment fit must be checked during evaluation. The OpenClaw local CLI reads a bounded evidence window; it is not an all-time or remotely authenticated ledger. Local Node’s static workflow inspection is not execution evidence. n8n partial editor runs are excluded; carried and pinned results are not reported again. A workflow revision can be unavailable, so revision-bound evaluation is not always possible.

Technical impact

SHADOW means no governance authority, not zero latency, zero failure risk or zero effect on runtime operation. The reference measurement above is limited to its stated synthetic workload and environment; it is not a formal quiet-qualified performance claim. Check behavior in your own authorized staging scope before considering a live deployment.

Data and security

Runtime observation uses bounded field contracts. Hosted also handles account, authentication, security and operational records, and configured verification can include selected business-rule facts. Identifiers can encode sensitive information. The Privacy notice describes collection, local storage, providers and deletion limits. There is no universal retention or backup-erasure guarantee, broad encryption-at-rest assurance, certification or external audit claim.

Access and use rights

A package download is not Hosted access. The approved-access sequence requires email verification, human review, invitation/account onboarding and pairing. Local Node also requires a signed installation manifest. Getting Started explains compatible operator-supplied origins and package-specific commands. Confirm activation and evidence delivery for your own installation; local status or successful pairing alone does not establish runtime delivery or a verified business outcome. Both public artifacts are Apache-2.0; Hosted and separately distributed services remain outside the OpenClaw artifact license.

Recovery and retention

Only fresh installation and compatible, closed-writer restore are established. Use observa stop to disable observation without deleting journals, proofs or workflow state. Full acknowledged v1 headers compact to the most recent 64 while durable identities and replay state persist; pending proofs remain, and the separate v3 path has configured retention limits. Do not assume indefinite full-header storage or cross-version recovery.

Qualification

Qualification means your implementation ran in SHADOW and met success criteria agreed in writing for a stated workflow version, environment and period. It is not a certification, guarantee or compliance determination.

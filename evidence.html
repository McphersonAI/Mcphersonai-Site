Public Benchmark & Evidence Standard v0.1.

This is the publication standard for benchmark claims on this site. No normalized benchmark result is published here. Release identity checks above are not performance benchmarks.

Identify the test and its scope

  • Give every result a stable benchmark ID and name the benchmark-standard version.
  • Identify the exact Observa version, source commit/tree where public and appropriate, and artifact hash. State whether the result applies to the current release or a historical one.
  • Identify the runtime and version, CPU, memory, operating system, storage and filesystem, container/VM layout, and network topology. Include where durable storage sits relative to the runtime and observer.
  • Declare warm/cold state, workload size, concurrency or requests per second, sample count and the workload class. Label workloads CONTROLLED SYNTHETIC unless a separately authorized class applies.

Define the measurement before running

  • Publish the precise timer start and stop events, the baseline and paired comparison, and which synchronous and asynchronous work is inside the timer.
  • For latency, report p50, p95, p99 and maximum, including absolute added latency. Relative workflow context may accompany those numbers only with a predeclared representative workflow profile.
  • Where capture applies, report expected and durable captures, loss, duplicates, refusals, corruption and join/integrity failures. Where correctness applies, state expected verdicts and the incorrect verdict count.
  • Predeclare the acceptance gate, run-selection rules and aggregation method. Report accepted and excluded runs with exclusion reasons. Do not select a favorable run after seeing the results.

Classify the whole result

  • Compute PASS, HOLD or FAIL mechanically using the predeclared gate. Each result defines the conditions for all three classifications.
  • Show the target, observations, what passed, what did not, confounders and known limitations. A favorable durability or correctness sub-result cannot override an unmet gate.
  • Gate changes require a new public standard/version and apply only to subsequent results. They never reclassify prior runs retroactively. Keep superseded and unfavorable published results accessible with their original labels.
  • Label evidence SELF-RUN until a third party has reproduced that exact result. Internal review is not independent external audit. Verification fixtures are FIXTURE CONFORMANCE, not qualified external verification or universal runtime support.

Make reproduction possible without exposing private data

  • Link the methodology and, where safe, a reproduction kit: scripts, synthetic fixtures or data, environment specification and run instructions.
  • Use dedicated test environments whose topology can be disclosed. Development or mixed-use measurements do not become canonical public performance claims.
  • Where safe, provide sanitized machine-readable artifacts with the same benchmark ID as the human page. Remove secrets, private hostnames/IPs, internal identifiers and customer or partner data.
  • Handle deliberately triggerable evidence-loss or security findings through coordinated disclosure. Repair or contain the issue before publishing exploit-enabling details.
  • Do not make named competitor performance comparisons at launch. Methodology, timer and topology differences must remain visible.

Canonical limitations.

This section is the single source for current website limitations. Read it with the release identities above and the scope of any individual evaluation.

Authority

SHADOW ONLY · AUTHORITY NONE · ENFORCEMENT OFF

Observa has no authority to block, approve or rewrite workflow actions. WOULD_DENY is counterfactual, not evidence that anything was blocked. Your existing authorization controls remain necessary.

Evidence and verification

AUTHORIZED != COMPLETED != VERIFIED. Runtime completion is not business-outcome verification; VERIFIED does not prove authorization. Outcome verification is still being qualified with founding workflows. Missing, unmapped or insufficient evidence stays unresolved. Fixture conformance is not external qualification.

Runtime and version scope

The public paths documented here are OpenClaw v0.7.4 and Local Node 0.1.7 for n8n. Exact environment fit must be checked during evaluation. The OpenClaw local CLI reads a bounded evidence window; it is not an all-time or remotely authenticated ledger. Local Node’s static workflow inspection is not execution evidence. n8n partial editor runs are excluded; carried and pinned results are not reported again. A workflow revision can be unavailable, so revision-bound evaluation is not always possible.

Technical impact

SHADOW means no governance authority, not zero latency, zero failure risk or zero effect on runtime operation. No normalized public latency or durability benchmark is published here. Check behavior in your own authorized staging scope before considering a live deployment.

Data and security

Runtime observation uses bounded field contracts. Hosted also handles account, authentication, security and operational records, and configured verification can include selected business-rule facts. Identifiers can encode sensitive information. The Privacy notice describes collection, local storage, providers and deletion limits. There is no universal retention or backup-erasure guarantee, broad encryption-at-rest assurance, certification or external audit claim.

Access and use rights

A package download is not Hosted access. The approved-access sequence requires email verification, human review, invitation/account onboarding and pairing. Local Node also requires a signed installation manifest. Getting Started identifies the public beta origin and package-specific commands. A fresh end-to-end production onboarding acceptance for both current packages is not established here. Confirm activation and evidence delivery for your own installation. Both public artifacts are Apache-2.0; Hosted and separately distributed services remain outside the OpenClaw artifact license.

Qualification

Qualification means your implementation ran in SHADOW and met success criteria agreed in writing for a stated workflow version, environment and period. It is not a certification, guarantee or compliance determination.

Read public artifacts in their original scope.

The released package documentation and CLI are the strongest current software references. The June 2026 Audit Mode schema and sanitized self-dogfood reconstruction (PDF) are historical artifacts. They illustrate known/unknown separation, not a benchmark or a qualified customer deployment.

The QSR origin story explains the workflow-first approach. Download counts are not used as evidence of customers, revenue or business outcomes.
